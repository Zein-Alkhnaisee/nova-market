# IMPLEMENTATION_LOG.md — NOVA Market

## 2026-09-08 — Phase 1: Foundation

**Stack initialized**: Vite + React 19 + TypeScript (strict), Tailwind CSS v4, Redux Toolkit + RTK Query, React Router v7, i18next/react-i18next, lucide-react, class-variance-authority.

**Architecture decisions**

- **Design tokens** live entirely in `src/index.css` as CSS custom properties, mapped into Tailwind's `@theme` so `bg-background`, `text-foreground`, `border-border`, `rounded-[var(--radius-lg)]`, etc. work directly in JSX. Components never hardcode hex values.
- **Light/dark theme**: implemented via a `ThemeProvider` React context + `localStorage`, not Redux — this keeps theme resolution synchronous and avoids a Redux round-trip on first paint (important for avoiding a flash of unstyled theme). Documented deviation from MASTER_SPEC §36, which lists theme under Redux global state; the effect is functionally identical for consumers (`useTheme()` is available anywhere) and switching is instant with no reload.
- **Language/RTL**: `i18next-browser-languagedetector` + `localStorage` persistence; a `LanguageProvider` syncs `<html dir>`/`<html lang>` on every language change so RTL is applied globally, not per-component. Same rationale as theme for not routing through Redux.
- **Cart / Wishlist / Compare**: implemented as Redux Toolkit slices (`features/cart`, `features/wishlist`, `features/compare`) since these are genuinely cross-cutting client state read by the Header, ProductCard, and multiple pages simultaneously.
- **Server state**: RTK Query `baseApi` uses `fakeBaseQuery()` with per-endpoint `queryFn`s reading from `mocks/data/*`, wrapped in an artificial `delay()` to produce realistic loading states. This preserves the exact RTK Query surface (hooks, tags, cache invalidation) a real `fetchBaseQuery` would have — swapping to a real backend later is a change to `baseApi.ts` and the endpoint bodies only, not to any consuming component.
- **Category system**: data-driven (`mocks/data/categories.ts`), not hardcoded into UI — new categories require no component changes, per MASTER_SPEC §4.
- **Routing**: every route from MASTER_SPEC §11 is registered now, even before its feature is built, so the app never 404s on a spec'd route. Unbuilt routes render `PagePlaceholder` inside the real `AppShell`, meaning header/footer/theme/i18n/RTL are already correct on every route from day one — only the page content is pending.

**Verification**: `tsc -b` clean, `oxlint` — 0 errors (3 advisory fast-refresh warnings from co-locating variants/hooks with components, acceptable), `vite build` succeeds (~253 KB main bundle gzipped ~80 KB, route-based code splitting via `React.lazy`).

**Deferred to a later phase**: MSW mock service worker (currently `queryFn` reads mock data directly, which is behaviorally equivalent for the UI but doesn't show up in the browser Network tab), Vitest/Playwright test setup, remaining i18n namespaces, all pages beyond Home/Shop/Product/Cart.

## 2026-09-09 — Phase 2: Search, Discovery, Wishlist

**What Phase 2 covers**: search (autocomplete, recent/trending, results page, filters/sort, URL sync), category-aware discovery on `/shop`, wishlist experience + persistence, compare experience, collections, plus a real test suite.

**Persistence layer**: `src/lib/persist.ts` (`loadPersisted`/`savePersisted`, try/catch-wrapped so a full or unavailable `localStorage` never crashes the app) is now actually wired up, not just written. `app/store/index.ts` subscribes to the store and mirrors `cart`, `wishlist`, and `recentSearches` slices to `localStorage` on every change, keyed as `nova:cart`, `nova:wishlist`, `nova:recentSearches`. Each slice's `initialState` reads from storage via `loadPersisted` so a reload restores exactly where the person left off.

**Search architecture decision**: rather than bolting search onto `productsApi`, a separate `searchApi` handles *autocomplete* (`getSearchSuggestions`) and *trending terms* (`getTrendingSearches`) — these are a different shape of query (fuzzy, small, fast, cached differently) from the *results* query, which reuses the now-extended `productsApi.getProducts` with `q`/`sort`/`minPrice`/`maxPrice`/`minRating`/`inStockOnly` params. This keeps the RTK Query cache tags clean: suggestion queries don't pollute the `Products` list cache, and vice versa.

**URL as the source of truth**: `SearchPage` and `ShopPage` both derive all filter/sort state from `useSearchParams()` — there is no local React state duplicating it and no Redux slice for it, per the architecture rule "URL state for shareable search/filter/navigation state." A `readFiltersFromParams` helper (duplicated intentionally in both pages rather than over-abstracted into a shared hook this early — revisit if a third page needs the identical shape) parses the params; `updateParams` mutates a `URLSearchParams` copy and calls `setSearchParams(next, { replace: true })` so filter tweaks don't spam browser history, while the initial `q` navigation does push a history entry (via `navigate()` from the search overlay).

**Search overlay accessibility**: implemented the ARIA 1.2 combobox pattern by hand (no headless-UI library added, to keep the dependency footprint the same as Phase 1) — `role="combobox"` on the input, `aria-expanded`, `aria-controls` pointing at the listbox, `aria-activedescendant` tracking the keyboard-highlighted option, `role="listbox"`/`role="option"` with `aria-selected`. Escape closes the dialog; arrow keys move `activeIndex`; Enter either selects the highlighted option or runs a full-text search with the raw input.

**Compare UX decision**: rather than only exposing `/compare` as a page someone has to know to visit, added a global `CompareBar` (rendered in `AppShell`, so it's present on every route) that appears once ≥1 product is selected for comparison and disappears when cleared — this was a deliberate product-discovery interaction addition beyond the literal spec text, in the spirit of "product discovery interactions" being a named Phase 2 priority.

**Testing**: Vitest + `@testing-library/react` + `@testing-library/user-event` + `jsdom` installed fresh (none of this existed after Phase 1). `src/test/setup.ts` adds jest-dom matchers, clears `localStorage` after each test, and polyfills `matchMedia` (missing in jsdom, needed by `ThemeProvider`). `src/test/renderWithProviders.tsx` is the shared test harness — wraps a component in a fresh Redux store + `MemoryRouter` + `I18nextProvider` so component tests don't need to hand-wire providers every time. 43 tests total: pure reducer logic (cart, wishlist, compare, recent searches — the highest-value, cheapest tests), `productsApi` filter/sort correctness against the real mock dataset, `ProductCard` interaction tests (add to cart, wishlist toggle, disabled state), and two page-level tests (`SearchPage` URL-sync round-trip, `ComparePage` empty/populated states) that exercise the URL-state architecture end to end rather than just unit-testing helpers in isolation.

**Verification**: `tsc -b` clean, `oxlint` — 0 errors (4 advisory fast-refresh warnings, same class as Phase 1's), `vitest run` — 43/43 passing, `vite build` succeeds (main bundle ~273 KB / gzip ~85 KB, route-based code splitting still intact — every new page is its own lazy chunk).

**Deferred to a later phase**: MSW, backend sync for cart/wishlist/orders, fuzzy/typo-tolerant search matching, dedicated `SearchOverlay`/`ShopPage` component tests, badge-filtered `/deals` `/new-arrivals` `/trending` routes.


## 2026-09-10 — Phase 4: Product Experience (+ closing Phase 2/6 gaps)

**Phase determination**: re-read MASTER_SPEC.md §107 and confirmed the exact phase list (Foundation → Home&Discovery → Categories&Shop → Product Experience → Search → Cart&Wishlist → Checkout → Account&Orders → Comparison&Collections → Smart → AI Assistant → Admin → Polish). Earlier sessions' informal "Phase 1"/"Phase 2" labels didn't map 1:1 to this list — cross-referencing against the actual repository showed Categories&Shop (3), Search (5), Cart&Wishlist (6, partial), and Comparison&Collections (9, partial) were already substantially built, while Product Experience (4) was still just the Phase-1 scaffold's minimal product detail page. Implemented Phase 4 in full, and used the opportunity to close two directly-related gaps flagged in the Phase 2 and Phase 6 checklists: Recently Viewed and Recommendations, since Product Experience's "recommendations" and "recently viewed" requirements are the same underlying feature.

**Data model change**: `ProductSummary` gained optional `images[]`, `description`, `specs` (a plain `Record<string,string>` — deliberately unstructured rather than a typed spec schema, since spec fields vary wildly by category and a rigid schema would fight the data more than help), and `variants` (`ProductVariantGroup[]`, currently `color`/`size`). All mock products got real (if brief) descriptions and specs; a subset got variant groups where it's realistic (headphones/laptop = color only, watch = color+size, shirt = color+size, bike = size only, controller = color only) rather than forcing every product to have variants.

**Reviews architecture**: `reviewsApi` holds review data in a module-level `let reviewStore` array (not a `useState`, not Redux) that starts as a copy of the mock seed data and gets appended to by `submitReview`. This is intentionally a "mock backend," matching the same pattern the spec's other `queryFn`-based endpoints use — a real backend swap only touches this file. Rating breakdown (1-5 star counts + average) is computed server-side-style inside the query rather than in the component, so the same computed shape would come back from a real API.

**Recommendation algorithm** (`recommendationsApi`): deliberately simple and explainable rather than "smart" in any ML sense — `getRelatedProducts` is same-category-first with a trending backfill so the rail is never sparse even for categories with only one product; `getPersonalizedProducts` derives category interest from the union of wishlist + recently-viewed product categories, excludes anything already interacted with, and falls back to trending items for a first-time visitor with empty state everywhere. This is explicitly the "Smart Features" phase's territory eventually (Phase 10), so this implementation is scoped as "good enough content-based recommendations for Phase 4/2," not a placeholder for the eventual smart-features pass.

**Local UI state vs. effects — a real bug avoided**: the first pass of `ProductDetailPage` called `setQuantity(1)` and `setSelectedVariants(...)` inside the same `useEffect` that dispatches `recordProductView`, to reset per-product UI state when navigating between products via the "You may also like" rail (same route, different `:slug`, so the component doesn't unmount by default). `oxlint`'s `set-state-in-effect` rule correctly flagged this as unnecessary cascading-render risk. Fixed by splitting the page into an outer `ProductDetailPage` (owns the query + loading/error states + the one legitimate effect: recording the view) and an inner `ProductDetailContent` component keyed by `product.id`. React's `key` prop forces a full remount when the product changes, so `quantity`/`selectedVariants` reset via their normal `useState` initializers with zero extra effects — a cleaner fix than the reset-in-effect pattern, not just a lint-silencing one.

**Testing**: added `recentlyViewedSlice` reducer tests, `reviewsApi` tests (breakdown math, empty-product case, submit-then-refetch round trip), `recommendationsApi` tests (exclusion from own related list, same-category preference, thin-category backfill, personalized exclude-list, trending fallback), and `ProductDetailPage` component tests (renders + records a view, variant selection updates ARIA state, quantity stepper, error state for an unknown slug). The shared `renderWithProviders` test harness gained a `path` option (defaults to `"*"`) so tests needing `useParams()` (like `:slug`) can register a real route pattern via `<Routes><Route path={path} .../></Routes>` instead of only relying on `MemoryRouter`'s location — a gap the previous session's harness had that just happened not to matter until a params-dependent page needed testing.

**Verification**: `tsc -b` clean, `oxlint` — 0 errors, 4 advisory fast-refresh warnings (same baseline as before this session — the new `set-state-in-effect` warning introduced by the first `ProductDetailPage` draft was fixed, not suppressed), `vitest run` — 60/60 passing (was 43), `vite build` succeeds (new `ProductDetailPage` chunk is ~13KB/3.7KB gzip on its own, everything still code-split per route).

**Deferred**: natural-language search (explicitly a separate Phase 5 sub-item, not started), smart cart recommendations rendered inside the cart page itself (Phase 6 partial), wishlist sub-collections and public/private visibility (Phase 9 partial, blocked on an account concept from Phase 8), a real error boundary component (Phase 1 gap, carried forward), dedicated component tests for `SearchOverlay`/`ShopPage`/`ReviewsSection` form/`QuickViewModal` (covered indirectly via API-level tests today).

## 2026-09-11 — Phase 7: Checkout

**Scope**: shipping, delivery, payment, review, order success — the full checkout flow, plus retrofitting the Cart page with the price breakdown checkout needs (subtotal/discount/shipping/tax/total, coupon input) so the numbers agree everywhere. This session also recovered from and fixed a real bug left over from the interrupted prior session (a wrong relative import path in `useCheckoutGuard.ts` that failed `tsc`).

**Payment boundary — the one rule that shaped the whole Payment step**: MASTER_SPEC's payment section is explicit that payment processing is backend territory and that a demo must never imply production security around card data. Concretely, this meant: card number/expiry/CVC/name are `useState` in `PaymentStepPage` only — never an action payload, never touch `checkoutSlice` (which is otherwise persisted to localStorage the same way cart/wishlist are), and the local state is reset to empty the instant a masked `{brand, last4}` summary is derived from it. That summary — not the card — is the only thing that travels forward, via React Router's navigation `state` (not Redux, not the URL, not localStorage) to the Review step, and from there into the `Order` record. Three separate tests assert this holds: a unit test on `ordersApi` that greps the serialized order for the literal test card number and expects no match, and the end-to-end `CheckoutFlow` test that does the same against the full Redux state tree and `localStorage` after a real order is placed through the actual UI.

**A real race condition, caught by a real integration test, not by inspection**: the first version of `ReviewStepPage.handlePlaceOrder` dispatched `clearCart()` and `resetCheckoutDraft()` *before* calling `navigate()` to the order-success page. `useCheckoutGuard('review')`'s effect depended on `[step, lines.length, shippingAddress, deliveryOption]`, so clearing the cart while still mounted on `/checkout/review` retriggered the guard's "cart is empty → go to /cart" branch, and — because Redux state updates and React Router's navigation are two independently-scheduled reconciliation sources — that guard-triggered redirect sometimes landed *after* the intended navigation to order-success, silently sending a person who just successfully completed checkout back to an empty cart page instead of their confirmation. Reordering the dispatches (navigate first) didn't fully fix it, because the guard's effect could still fire on a stale render before the route swap committed. The actual fix: `useCheckoutGuard`'s effect now depends only on `[step]` — it checks prerequisites once when a step is *landed on*, not continuously as the store changes underneath an already-mounted page. This is the more correct semantics anyway: a guard's job is to stop someone from arriving at a step without what it needs, not to react to a page's own "advance to the next step" action changing the very state the guard reads. Caught by the `CheckoutFlow` end-to-end test, not by manual review — worth noting since it's exactly the kind of bug that a scaffolding-only test suite (state in, state out) wouldn't have found; only actually driving the full flow through real routing surfaced it.

**Guard architecture**: `useCheckoutGuard(step)` is one hook shared by all four step pages rather than four separate ad-hoc redirect checks, encoding the step dependency chain explicitly (delivery needs shipping; payment and review need both). Landing directly on `/checkout/review` via a typed URL with nothing in the checkout draft correctly bounces to `/checkout/shipping` (or `/checkout/delivery`, whichever prerequisite is missing first) rather than crashing on a null shipping address — six scenarios covered in `useCheckoutGuard.test.tsx`.

**Pricing as a single shared function**: `lib/pricing.ts`'s `computePricing()` is the only place subtotal/discount/shipping/tax/total math happens — Cart, Review, and (by copying the already-computed numbers from the placed `Order` record, not recomputing) Order Success all render from it. This was a deliberate reaction to a common real-world bug class: cart and checkout showing different totals because two different components each reimplemented the arithmetic slightly differently.

**Coupon UX decision**: applying a coupon in the Cart page and having it still be applied on the Review page (and vice versa) works because `checkoutSlice.couponCode`/`discountPercent` is the single source of truth for both — `CouponInput` is a dumb, reusable component with no state of its own beyond the text field, matching the same "shared component, single source of truth" pattern as `OrderSummary`.

**Testing**: `lib/pricing.ts` (7 tests covering the free-shipping threshold, discount-before-tax ordering, non-negative total floor), `lib/validation.ts` (postal code/phone/card/expiry/CVC/brand-detection, 6 tests), `checkoutSlice` reducers (5 tests), `useCheckoutGuard` (6 tests, one per prerequisite-missing scenario plus the two happy-path landings), `ordersApi` (5 tests: order-number format, pricing embedded correctly, localStorage persistence, newest-first ordering, and the no-raw-card-data assertion), and the `CheckoutFlow` end-to-end test (drives the real UI through all 5 screens via `userEvent`, asserts the final state).

**Verification**: `tsc -b` clean, `oxlint` — 0 errors, 4 advisory fast-refresh warnings (unchanged baseline), `vitest run` — 91/91 passing (was 60), `vite build` succeeds (each checkout step is its own lazy-loaded chunk, 2–5KB each; `CheckoutLayout` itself isn't a separate chunk since it's imported directly rather than lazily).

**Deferred to Phase 8 (Account & Orders)**: the Order Success page's "View order" link points at `/account/orders/:id`, which is still the Phase 1 placeholder — a real order-detail page showing the same `Order` record is Phase 8's job, not Phase 7's, since order *history* and *detail views* are explicitly an Account concern in the spec's phase split. Billing-address-different-from-shipping is collected as a checkbox on the Payment step but doesn't yet reveal a second address form when unchecked — documented as a known simplification (not a silent gap) since building a second full `AddressForm` flow felt like scope creep beyond what Phase 7's checklist actually asked for; worth revisiting if a future session has room.

## 2026-09-12 — Phase 8: Account & Orders

**Scope**: login, register, forgot/reset password, logout, account shell, overview, profile, addresses, payment methods, settings, orders list, order detail. This also resolved the Phase 7 gap where Order Success's "View order" pointed at a placeholder.

**Mock auth boundary**: `services/api/authApi.ts` is the single file that would be replaced by a real auth service. It's written as real async RTK Query mutations with genuine error paths (wrong password → 401, duplicate email → 409) so every consumer — the login form's error alert, the register form's duplicate handling, `useAuthGuard`, the account pages — is already shaped the way it would be against a real backend. The file carries a prominent comment stating that passwords are stored in plain text in a localStorage mock, which a real backend must never do. Per MASTER_SPEC §29 ("Never fake successful authentication in a way that implies production security"), this is deliberately called out rather than hidden. `forgotPassword` succeeds regardless of whether the email exists — that's not laziness, it's the correct behavior for a real implementation too, since a differentiated response leaks which emails have accounts.

**A real bug found by a test, and fixed at the root**: `addressesSlice`'s "set this address as default" test failed with two addresses flagged default simultaneously. The reducer logic was correct; the actual cause was ID generation. Every record in the project used `` `${prefix}-${Date.now()}` `` — so two addresses added within the same millisecond received *identical IDs*, and anything keyed by ID (React list keys, set-default, remove) then operated on the wrong record, or on both. This was latent across five call sites: addresses, payment methods, orders, reviews, and user registration. Rather than fudging the test with a delay, I added `lib/id.ts` (`generateId(prefix)` — timestamp plus a monotonic counter) and replaced all five. A regression test asserts three back-to-back address additions produce three distinct IDs. Worth flagging because this class of bug is nearly invisible in manual testing — a human clicking "add address" twice will never hit the same millisecond, but a fast script, a double-click, or a restored-from-backup batch import absolutely would.

**Guard consistency**: `useAuthGuard` follows the same once-per-landing pattern established by `useCheckoutGuard` in Phase 7, and for the same reason — a guard that re-fires reactively would misbehave the moment a page's own action changes the guarded state (here: signing out from Settings, which would otherwise race the intended navigation home). It also captures the current path into `?redirect=`, so being bounced to login and then logging in returns you where you were headed rather than dumping you on a generic account page.

**Payment methods and the payment boundary**: the account's saved-cards feature reuses the same discipline as the checkout Payment step — the raw card number lives only in local component state, and only `{brand, last4, expiry}` is ever dispatched to Redux or persisted. A test asserts the persisted record's keys are exactly `brand/expiry/id/isDefault/last4` and that the full test card number appears nowhere in it.

**Order cancellation models real constraints**: `cancelOrder` refuses any order past `processing` (i.e. already shipped/delivered/cancelled/refunded), returning a 409 rather than optimistically flipping the status. This mirrors what a fulfilment backend would enforce and keeps the UI honest — the Cancel button only renders for genuinely cancellable statuses, and the mutation independently rejects the rest rather than trusting the UI to have hidden the button.

**Reused rather than rebuilt**: the account Addresses page reuses checkout's `AddressForm` wholesale; order detail and order success both render the shared `OrderSummary`; order status badges reuse the existing `Badge` primitive with a status→tone map. No parallel architecture was introduced. `/account/wishlist` was adapted (its own page-level container and `h1` removed) to sit correctly inside `AccountLayout` rather than being duplicated.

**One route left deliberately as a placeholder**: `/account/collections`. Reusing the existing editorial `CollectionsPage` there would have been visually plausible but semantically wrong — editorial collections are curated merchandising, while the spec's Phase 9 "wishlist collections" are user-created and have public/private visibility. Rendering the wrong feature to make a route look finished would be worse than an honest placeholder that names the phase it belongs to.

**Verification**: `tsc -b` clean, `oxlint` — 0 errors and 4 advisory fast-refresh warnings (unchanged baseline), `vitest run` — 121/121 passing (was 91), `vite build` succeeds with every new page code-split into its own 0.5–6 KB chunk.

**Also this session**: `MASTER_SPEC.md` and `DESIGN_SYSTEM.md` were moved from `docs/` to the project root, and `HANDOFF.md` was created, so a new AI session or a different tool can pick the project up from the repository alone without needing the original uploads.

## 2026-09-15 — Phase 9: Comparison & Collections (completing the wishlist-collections gap)

**Scope**: this phase's Compare feature (comparison table, global `CompareBar`) and editorial Collections (`/collections`, `/collections/:slug`) were already built in an earlier session. What remained, per `HANDOFF.md` §7, was specifically user-created wishlist collections and public/private visibility — deferred until Phase 8 introduced an account concept, since collection ownership needs a signed-in person.

**Kept genuinely distinct from editorial collections**, per explicit instruction: `userCollectionsSlice` is a new slice, `UserCollection` is a new type, the pages live under `pages/account/` rather than `pages/collections/`, and they share no components with `CollectionsPage`/`CollectionDetailPage`. The only shared surface is the `collections` i18n namespace, organized so the existing editorial keys (`title`, `subtitle`, `viewCollection`, …) are untouched and the new feature's strings live under a nested `yours.*` key — a deliberate choice to avoid maintaining two near-identical translation files for what's conceptually one "collections" concern, while keeping the key names unambiguous about which feature they belong to.

**Privacy design for the public share link**: `/c/:id` is intentionally structured so a collection that doesn't exist and a collection that exists but has been set private render the *exact same* not-found component with the *exact same* copy. This isn't an incidental simplification — a link that behaved differently for "doesn't exist" vs. "exists but is private" would let someone probe for the existence of private collections by trying ids and watching for a different error. Asserted directly by a test (`PublicCollectionPage.test.tsx`) that creates a private collection and confirms its name never appears in the not-found render.

**Honest limitation, documented rather than glossed over**: "public" in this frontend-only demo means "reachable via a link within this browser's own localStorage," not "reachable by anyone on any device" — there's no backend for the link to actually fetch shared data from elsewhere. This is the same mock-backend boundary every other feature in this project has (orders, reviews, auth), not a shortcut specific to collections, and it's called out plainly in `PROGRESS.md` rather than left for someone to discover by testing the share link on a second device.

**Membership toggling reuses the established idempotency pattern**: `addProductToCollection` is a no-op if the product is already a member (mirrors `wishlistSlice`'s dedupe logic from earlier phases), so `AddToCollectionMenu`'s checkbox-style toggle can dispatch freely without needing to pre-check state client-side.

**`AddToCollectionMenu` is scoped to the Wishlist page only**, not added to `ProductCard` globally. The spec's ask is "wishlist collections" — organizing *saved* items — not a collection-adding affordance on every product card sitewide. Keeping it scoped avoids a speculative feature-creep addition to a component (`ProductCard`) that's reused across Home, Shop, Search, Compare, and Collections.

## 2026-09-17 — Phase 10: Smart Features

**Scope determination**: MASTER_SPEC §10 lists exactly seven items — personalized recommendations, recommendation reasons, smart filters, product configurator, smart cart suggestions, command/quick actions, feature flags — and cross-referencing showed most of these were genuinely unbuilt, not just "covered by existing work" as might have been assumed from Phase 2/4's recommendation rails. Only "personalized recommendations" itself was already done; the other six were new. Each of the terse phase-list bullets had a fuller, numbered section elsewhere in the spec (§24 Smart Cart, §32 Product Configurator, §81 Feature Flags, §86 Command/Quick Action Experience, §89 Smart Recommendation Reasons) that was read before implementing, rather than guessing at scope from the one-line bullets.

**Recommendation reasons — a new return type, not a bolted-on field**: `recommendationsApi` now returns `RecommendedProduct[]` (a `ProductSummary` plus a `reason: string`) instead of plain product arrays, so it's visible at the type level which queries produce reasoned recommendations. Reasons are genuinely differentiated by *why* a product is being shown — same-category match ("Popular with X shoppers"), price-based alternative when backfilling a thin category, trending fallback, interest-category match for personalized picks — rather than a single decorative caption slapped on everything. `ProductRail` gained a `showReasons` prop so existing unreasoned call sites (e.g. Home's badge rails) are unaffected.

**Smart filters — counted against the right base set, not the visible results**: `FilterPanel`'s new `facetBaseProducts` prop is deliberately *not* the currently-filtered result list — it's everything matching category/search/price but before rating/stock narrow further. Counting against the already-filtered list would make every remaining option's count trivially equal the current result count, which isn't useful; counting against the pre-rating/stock set answers the actually useful question ("how many results would picking 4★+ leave me with"). This costs an extra `useGetProductsQuery` call per page (Shop, Search) with the same params minus `minRating`/`inStockOnly` — accepted as a reasonable cost for correctness over a single combined query that couldn't distinguish the two facets cleanly.

**Product configurator — a genuinely different feature from variants, not a relabeling**: the existing `VariantSelector` (color/size swatches with no price impact) was left untouched; `ProductConfigurator` is new and handles what MASTER_SPEC §32 actually describes — option *groups* where each option carries a `priceDelta`, and the product's displayed and cart price is the base price plus the sum of selected deltas. Two mock products carry real `configuratorGroups`: the existing Kite laptop (memory/storage/processor) and a new "Nova Forge Custom PC" product built specifically to exercise the spec's PC example (CPU/GPU/RAM/storage/cooling/case, 6 groups). On the PDP, a configurable product shows the configurator *instead of* the variant selector (a product isn't both in this data model — a reasonable simplification, not a limitation the architecture forces).

**A cart-line identity bug, caught before it shipped, not after**: adding configurator support meant a product could now be added to the cart at more than one price (base vs. differently-configured). The first pass didn't account for this — `addToCart`'s merge logic keyed on `productId` alone, so adding two different configurations of the same laptop would have silently merged into one cart line at whichever price happened to be dispatched second, and `removeFromCart`/`setQuantity` (keyed the same way) would have affected *all* lines of that product simultaneously, including differently-configured ones. Caught while wiring the Cart page's `<li key={line.productId}>` — the key collision made the underlying data-model problem visible immediately. Fixed by extending `CartLine` with an optional `configurationSummary` and re-keying all three cart reducers on `(productId, configurationSummary)` — an unconfigured line (`configurationSummary: undefined`) still merges/matches only with other unconfigured lines of the same product, so ordinary (non-configured) add-to-cart behavior from every earlier phase is unchanged. Seven dedicated tests cover this: configured price storage, two configurations staying separate, identical configurations merging, configured vs. unconfigured never merging, removing one configuration not touching a sibling, quantity changes not cross-affecting siblings, and subtotal correctness across mixed lines.

**Command palette — remount-over-reset-in-effect, applied to a third component**: the first draft reset `query`/`activeIndex` inside the same effect that toggled `open`, which `oxlint`'s `set-state-in-effect` rule flagged — the same class of issue fixed in `ProductDetailPage` (Phase 4) and present but historically accepted in `SearchOverlay` (Phase 2). This time it was fixed rather than added to the accepted baseline: split into an outer `CommandPalette` (owns `open` state, the global keydown listener, and a `document.body.style.overflow` side effect — a genuine external-system sync, not a lint violation) and an inner `CommandPaletteDialog` keyed by an incrementing `instanceKey`, so `query`/`activeIndex` initialize fresh via ordinary `useState` on every open with no reset effect needed. Lint warnings stayed at the same baseline of 4 (not 5) as a result.

**Feature flags — designed to be exercised, not just declared**: `src/config/features.ts` defines the five flags from MASTER_SPEC §81's own example list. The meaningful design decision was making at least one flag (`productComparison`) actually change what renders — hiding the compare button on every `ProductCard`, the floating `CompareBar`, and the Compare links in both desktop and mobile nav — rather than only wiring flags to genuinely-new Phase 10 features where "off" would be indistinguishable from "not built yet." A flags system that only gates brand-new code doesn't prove the gating mechanism actually works; gating something pre-existing and well-tested (Compare, shipped in Phase 9) makes the on/off behavior independently verifiable. `smartRecommendations` and `productConfigurator` gate their own new Phase 10 surfaces (reasons, cart suggestions, the configurator) the same way. Settings' new "Experimental features" section is the toggle UI, reading and writing the same `featureFlagsSlice` everything else reads.

**Testing**: 47 new tests across 8 new files — `featureFlagsSlice` (default/override/reset/independence), `recommendationReasons` (reason presence and correctness across all three recommendation endpoints, cart-suggestion exclusion and dual reasoning), `cartConfiguredLines` (the 7 tests described above), `FilterPanelSmartFilters` (counts, zero-result disabling, graceful fallback with no facet base), `ProductConfigurator` (full PDP integration — rendering, default price, live price updates, cart integration, and that a non-configurable product is unaffected), `CommandPalette` (keyboard shortcuts on both Ctrl and Meta, Escape, accessible roles, filtering, no-results state, action execution, arrow+Enter navigation, flag gating), `SettingsFeatureFlags` (toggle list, unchecking, re-checking), and `FeatureFlagGating` (Compare UI on/off end to end). Two test-writing mistakes were caught and fixed during this pass, not shipped: an over-specific `getByText` query matching two elements in `CompareBar` (fixed to `getAllByText`), and a personalized-recommendations reason test that assumed no trending backfill would occur for a category with only 2 products at the default limit of 4 (fixed by requesting `limit: 2` to test the category-match reasoning in isolation from the backfill it was never asserting about). The shared `renderWithProviders` test harness gained a `ThemeProvider` wrapper, previously missing, needed by `CommandPalette` and by any future test of theme-aware components.

## 2026-09-20 — Phase 11: AI Shopping Assistant

**Scope determination**: read MASTER_SPEC §11's phase-list bullets (assistant UI, floating assistant, dedicated assistant page, conversation UI, suggested prompts, product recommendations, comparison actions, mock AI service, AI API abstraction) together with §30's fuller spec (the `AssistantMessage`/`AssistantAction` data shapes, the `POST /assistant/messages` endpoint, and the explicit requirement that the frontend "must not tightly couple itself to a specific AI provider"). All 9 items were genuinely unbuilt — `/assistant` was a placeholder route, referenced only by the Header link and a flag-gated (but non-functional) command-palette action.

**AI API abstraction — the one requirement that shaped everything else**: `services/assistant/aiProvider.ts` defines a single-method `AIProvider` interface (`sendMessage(history, userMessage): Promise<AssistantMessage>`). `mockAIProvider.ts` implements it with rule-based intent matching; `assistantApi.ts` (the `POST /assistant/messages` equivalent) depends only on the interface, not the mock implementation directly re-exported. A real LLM integration replaces `mockAIProvider` in one place — every component (`ConversationView`, `AssistantActionButtons`, both the floating panel and the dedicated page) is written against `useAssistantConversation` → `assistantApi` → `AIProvider`, never against the mock's internals.

**One assistant architecture, not two**: the floating panel and the dedicated `/assistant` page both render the same `ConversationView` component (a `compact` prop adjusts padding, nothing else differs), both read from the same `useAssistantConversation` hook, both dispatch into the same `assistantSlice`. This was an explicit instruction carried over from the prior Phase 10 session's HANDOFF notes and was followed literally — there is no separate "mini assistant" state machine.

**Comparison and recommendation actions reuse existing slices, not parallel ones**: `AssistantActionButtons` dispatches `toggleCompare` from the existing `compareSlice` (Phase 9) and `addToCart`/`toggleWishlist` from the existing `cartSlice`/`wishlistSlice` (Phase 6) directly — the assistant doesn't have its own notion of "what's in compare" or "what's in the cart," it just triggers the same actions a `ProductCard` click would. A "compare X and Y" response's `view_comparison` action adds both matched products to `compareSlice` and navigates to the real `/compare` page (Phase 9's comparison table), which is the actual requirement behind "comparison actions," not a bespoke in-chat comparison view.

**Mock AI service — rule-based, not a stub, with an honestly documented limitation**: `mockAIProvider` handles six distinct intents (greeting, budget+category, compare, specs/explain, gift, keyword fallback) over the real product catalog, each producing a genuinely different response shape — some return products with actions, some return explanatory text only, some ask a clarifying follow-up. It is explicitly *not* claimed to be more capable than it is: category-based matching (`laptop`/`computer`/`pc`/`keyboard` → `computers`) doesn't distinguish product *type* within a category, so "find me a laptop under $1000" can legitimately surface a mechanical keyboard, since both are `computers` category and the keyboard is the only in-budget match. This was caught by a test that initially (incorrectly) expected the $1,399 Kite laptop to appear under a $1,000 budget — the test's expectation was wrong given the actual, correct filtering behavior (price ≤ budget is a hard constraint, and $1,399 > $1,000), not the implementation. The test was corrected to expect the keyboard; the category-granularity limitation itself was left as-is and documented in PROGRESS.md, not "fixed" by inventing per-product-type tagging that MASTER_SPEC's mock-backend philosophy doesn't ask for.

**Real bugs found and fixed during test-writing, distinguished from test bugs**:
1. **Genuine implementation bug**: `AssistantActionButtons` rendered "Add to cart" as clickable the instant the message rendered, before the underlying `useGetProductsQuery()` fetch (which `cartSlice.addToCart` needs a full `ProductSummary` from, not just an id) had resolved. A fast click within the ~300ms mock-fetch window would find `allProducts` still `undefined` and silently do nothing — no error, no feedback, just a no-op. Reproduced reliably in isolation (a minimal debug test outside the full conversation flow) before fixing, to rule out a test-timing artifact rather than a real defect. Fixed by disabling *only* the `add_to_cart` button (not `add_to_compare`/`add_to_wishlist`/`view_product`/`search`, none of which need the fetched product list) while `productsLoading` is true, with `aria-busy` set and the existing `disabled:opacity-50` token-based styling from the design system — no new visual language invented. A dedicated regression test (`AssistantActionButtons.test.tsx`) asserts the disabled→enabled transition explicitly and that add_to_compare is unaffected by the same loading state.
2. **Two test bugs, not implementation bugs**: (a) an action-filter assertion checked `add_to_cart`/`add_to_compare`/`view_product` actions by filtering on `payload === product.id`, but `view_product`'s payload is deliberately the product *slug* (it's a route param), not the id — corrected the assertion to check `view_product` separately by slug rather than changing the (correct) implementation. (b) `detectBudget`'s regex required 2–6 digits, silently failing to parse single-digit budgets like "$5" — this one *was* a real parsing bug (not just a test error) and was fixed by widening the regex to `\d{1,6}`. (c) the category-keyword map was missing "gamer" (only had "gaming"/"console"/"controller") — also a real gap, fixed by adding it.

**Testing**: 26 new tests across 5 new files — `mockAIProvider` (13 tests covering every intent handler and edge case), `assistantSlice` (3), `assistantApi` (2, including that conversation history passed to the provider is never mutated), `AssistantPage` (6, end-to-end through real routing: suggested prompts, typed messages, add-to-cart reaching the real cart, a comparison action populating the real compare list and navigating, clearing the conversation), `AssistantActionButtons` (2, including the loading-race regression), and `FloatingAssistant` (6: visible on ordinary routes, hidden on checkout/auth/the assistant page itself, hidden when `aiAssistant` is off, opens/closes).

**Verification**: `tsc -b` clean, `oxlint` — 0 errors, 4 advisory warnings (unchanged baseline — no new warnings from any Phase 11 file), `vitest run` — 219/219 passing (was 187), `vite build` succeeds with `AssistantPage` and every assistant component correctly code-split.

**Deferred**: nothing from MASTER_SPEC §11's actual scope — all 9 listed items are implemented and reuse existing architecture where the spec calls for it. The category-granularity limitation in the mock AI (documented above) is the only noteworthy gap, and it's a mock-backend characteristic, not a missing feature — a real AI provider behind the same `AIProvider` interface wouldn't have it.
