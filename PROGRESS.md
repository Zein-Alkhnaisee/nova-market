**Kept distinct as required**: `/collections` (editorial, curated by the store) and `/account/collections` (user-created, owned by a signed-in person) share no components, no Redux state, and no i18n keys beyond the parent `collections` namespace being reused for organization — verified there is no code path where one page can render the other's data.

**Known limitation, stated plainly**: this is a frontend-only demo with no backend, so "public" only means "accessible via a link to anyone using this same browser" — the collection data lives in this browser's localStorage, not on a server. A real public-sharing feature needs the collection data to live somewhere reachable by other browsers/devices. The visibility flag, the distinct public route, and the privacy-safe not-found behavior are all implemented exactly as specified; only the "reachable from a different device" part requires a real backend, which is out of scope for every feature in this project, not unique to this one.

**A real bug found and fixed, not shipped**: the first version of `AssistantActionButtons` rendered "Add to cart" as immediately clickable regardless of whether the product catalog fetch had resolved yet — since `cartSlice.addToCart` needs a full `ProductSummary`, not just an id, clicking before the ~300ms mock-fetch completed silently did nothing. Fixed by disabling that specific button (only that one — `add_to_compare`/`add_to_wishlist`/`view_product`/`search` don't need the fetched list) while `productsLoading` is true, with a dedicated regression test asserting the disabled→enabled transition and that a click after enabling actually reaches the cart.

## Known issues / deliberate deferrals
- **The mock AI's replies are English-only text**, including a literal `$` in its budget wording (`mockAIProvider`). Everything around it (labels, buttons, cards, prices) is translated and locale-formatted; the assistant's own sentences are not. A real provider behind `AIProvider` would answer in the user's language. (Dates and the checkout shipping price were fixed in Phase 13.)
- **Phase 13 left out, deliberately:** per-page SEO titles and product metadata; Framer Motion animations; a performance pass; a mobile bottom navigation bar (MASTER_SPEC §67 — a new feature, not polish); a mobile layout for the admin area (tables scroll horizontally).
- Analytics: per-browser data; one period at a time (no comparison with the previous period); daily buckets for every range; top products capped at 8; product/category sales are line-item sales (before discounts, shipping and tax) so they don't sum to revenue; categories are attributed from the CURRENT catalog; Conversion "Not available".
- **Still never checked in a real browser (all of Phases 1–13) across RTL / mobile / dark.** Phase 13 did a static audit and fixed what it found; that is not a visual review. Arabic strings (`src/i18n/locales/ar/`) are functional but unreviewed by a native speaker.
- Coupons: codes can't be changed after creation; no expiry dates, usage limits, minimum spend or per-customer rules; the delete-409 only protects against orders that recorded the code (`Order.couponCode` is new — older orders carry none, so their usage is unknowable); checkout does not re-validate an already-applied coupon at order placement (pre-existing), so a coupon deactivated or deleted after being applied in a cart still goes through; edits are per-browser.
- Admin Orders: the list is not paginated (fine for the mock, would need server-side paging on a real backend); sorting is newest-first only. Orders with no linked account are marked "No account" (placed as a guest before checkout required sign-in, or before orders were linked to accounts).
- Orders (admin): status changes are status-only — no money moves on a refund, no tracking numbers, notes, bulk updates or date-range filter, and no customer notification. **Orders and admin status changes do not touch product inventory**: placing an order doesn't decrement `inventory`, and cancelling/refunding doesn't restock it (the catalog store and order store are independent). `placeOrder` creates orders as "confirmed", so "pending" is never an at-rest status in this mock (it exists in the timeline and the rules). The admin sees only orders stored in the current browser.
- Categories: slugs are fixed at creation (the storefront relies on id === slug); there is no parent/sub-category editing — seed categories have none and a nested category would appear as a top-level item in the storefront's flat category rail; deleting is a hard delete (only possible when empty) and per-browser only. Category images are stored but the storefront doesn't display them.
- Test infrastructure: the full suite takes ~100 s on a normal machine but exceeded a 300 s limit on a single-core sandbox, so it was verified in three chunks (unit, components A, components B — 57 files total, all covered). One run saw the pre-existing `ProductConfigurator` test fail once (its `waitFor` uses RTL's 1000 ms default and it failed at ~1045 ms); it passed in every rerun. Believed to be a timing flake under load; not proven, and the test was not modified.
- Product catalog: edits and archives persist per-browser only (localStorage `nova:products:v1`), like every other store here. Wishlist/collection/header counts that are derived from stored ids can exceed the number of products shown once something is archived (HANDOFF §11). Cart lines carry their own snapshot and are not revalidated against the catalog, so an archived product already in a cart can still be ordered. Product rating and review count are not editable (new products start at 0). Changing a product's main image drops its gallery. No bulk actions, no image upload (URL only), and no per-variant or configurator editing in the admin form.
- Admin dashboard: the Conversion KPI is unavailable (no visit/session tracking, so there is no honest denominator). Orders placed as a guest, or before `customerId` existed, can't be attributed to an account; the Customers list counts and flags them instead of hiding them. The dashboard's "Customer" column in Recent orders is the shipping recipient's name, not a resolved account. Dashboard product counts currently read the static product mock and will move to the admin product store at the Products checkpoint. Admin only sees orders and accounts stored in the current browser (same localStorage boundary as everything else).
- Smart filters only compute counts for rating and in-stock — price range isn't counted/disabled dynamically (the numeric inputs don't lend themselves to discrete option counts the same way).
- Only 2 of 9 mock products have configurator groups (the Kite laptop and the new Nova Forge Custom PC) — intentional, since MASTER_SPEC's configurator examples are specifically laptop/PC, not every product category.
- Feature flags persist per-browser only, same localStorage-based mock-backend boundary as every other piece of state in this project — there's no server-side remote-config system to fetch flags from.
- The command palette's action list is fixed (search/cart/wishlist/theme/language/assistant) rather than fuzzy-searching site content (products, orders, pages) — a reasonable v1 scope for "quick actions," not exhaustive command-driven navigation.
- Notification toggles in Settings are local-only (no backend to persist them to) and are deliberately not written to Redux/localStorage rather than pretending they saved.
- **MSW and Playwright (MASTER_SPEC §105) are intentionally not installed.** MSW: `queryFn` reads the in-repo mock layer directly, which is behaviorally identical for the UI (loading, error, cache tags, invalidation) but requests don't appear in the Network tab; HANDOFF §8 #1 keeps the swap-to-real-backend surface in `services/api/*`. Playwright: behaviour is covered by Vitest + Testing Library driving real routing; a browser-based suite is worth adding together with the first real-browser review, because that is the gap it would close (it needs a browser binary and a dev server the build sandboxes here don't have).
- Cart/wishlist/orders/reviews are not synced to any backend/account — persistence is local-device-only (localStorage), and submitted reviews only last the session (in-memory mock store).
- Search suggestions match on product name/brand and category name only — no fuzzy matching/typo tolerance, and no natural-language parsing (Phase 5 explicitly calls this out as a separate sub-item).
- No dedicated component tests yet for `SearchOverlay` (autocomplete keyboard nav), `ShopPage`, `ReviewsSection` form submission, or `QuickViewModal` — indirectly covered via API-level tests since they share the same underlying logic, but dedicated tests would still be valuable.
